# はんなりdev マーケティング計画（marketing-plan）

作成日: 2026-11-22
対象: はんなりdev ポータル（ランディングページ）を中心とした集客・問い合わせ獲得
関連: `../dev-plan/dev-plan.md`（開発計画）

> **この計画の前提と未確定事項**
> サイトの記述から読み取れる内容と、一般的な小規模開発会社の集客手法をもとにした**たたき台**です。ターゲット顧客・予算・目標件数・実績の公開可否は未確認のため、「5. 決めること」で確定させてください。数値目標は仮置きです。

## 1. 現状整理

### 1.1 事業とポジショニング（サイトの記述より）

| 項目 | 内容 |
| --- | --- |
| 事業 | ソフトウェア・Web開発、ITコンサルティング（要件定義・技術選定・計画策定の支援） |
| 規模 | 小さな会社。一つの案件に設計者として深く関わる |
| 打ち出し | 「建物を設計するように、システムを設計する。」要件定義を設計の中心に置き、長く使える仕組みを作る |
| 進め方 | ヒアリング・要件定義 → 設計 → 実装 → 検証 → 運用・保守（相談から保守まで一貫） |
| 分野 | 業務システム／Webサービス／Webサイト／ITコンサルティング |
| 差別化の軸 | 「作って終わりにしない」「設計力」「小さな会社ならではの一貫した関与」 |

### 1.2 資産と弱み

| 強み | 弱み・制約 |
| --- | --- |
| 思想が明確で一貫したメッセージ | 個別の実績・導入事例・顧客名を掲載していない（信頼の根拠が弱い） |
| 建築モチーフのイラストによる独自のビジュアル | 会社の所在地・代表者・連絡先が未公開（BtoB では不安要素） |
| 静的サイトで高速・低コスト運用 | Journal に記事がなく、検索流入の入口がほぼ無い |
| GTM 導入済み（計測の土台あり） | フォーム送信先が未設定（公開時点では問い合わせが届かない） |

**最優先の前提**: フォーム（または連絡手段）が機能することが、すべての施策の前提です。開発計画フェーズ1を先に完了させます。

## 2. 目標

仮置きの数値です。公開後 1〜2 か月の実績を見て調整します。

| 期間 | 目標 | 指標 |
| --- | --- | --- |
| 公開〜3か月 | 計測・導線を整え、**問い合わせを受けられる状態**にする | フォーム送信が計測できる。月間セッションの基準値を把握 |
| 〜6か月 | 検索・紹介経由の流入を作る | 月間問い合わせ **1〜2 件**、Journal 記事 **6 本以上** |
| 〜12か月 | 継続的に案件相談が来る状態にする | 月間問い合わせ **3〜5 件**、受注につながる商談 **年 2〜4 件** |

## 3. ターゲットとメッセージ

### 3.1 ターゲット（仮説。要検証）

| # | ターゲット | 困りごとの例 | 提供価値 |
| --- | --- | --- | --- |
| A | **中小企業の経営者・業務責任者**（地元・関西圏を優先） | 属人化した業務を仕組み化したいが、何から頼めばよいか分からない | 業務の棚卸しから要件整理・開発・保守まで相談できる窓口 |
| B | **IT 部門が小さい／無い企業の担当者** | 外部ベンダーへの発注で要件がずれる、失敗した | 要件定義を中心に据えた、認識のずれを防ぐ進め方 |
| C | **スタートアップ・新規事業担当** | 小さく始めて育てたい。技術選定に自信がない | 小さく始めて育てる Web サービス開発、技術選定の助言 |

最初は **A と B を主ターゲット**とし、関西圏（大阪）を中心に据えることを推奨します。サイトのモチーフと「はんなり」という屋号が、地域性と親和します。

### 3.2 コアメッセージ

- 一言: **「建物を設計するように、システムを設計する」**（現行維持）
- 補強する 3 点:
  1. **要件定義から保守まで同じ担当者が見続ける**（小さな会社の強み）
  2. **作る前に全体像を共有する**（設計レビューで認識を合わせる）
  3. **長く手を入れ続けられる構造**（保守を前提にした設計）
- 避けること: 実績のない誇大な表現、他社の比較・批判

## 4. 施策

### 4.1 土台整備（公開前〜公開直後）

| 施策 | 内容 | 優先度 |
| --- | --- | --- |
| 問い合わせ導線の確立 | フォーム送信先設定、送信完了の計測、自動返信メール、24 時間（営業日）以内の返信ルール | 必須 |
| 信頼情報の追加 | 所在地（番地まで出せない場合は市区町村）、代表者名・プロフィール、連絡先、プライバシーポリシー | 必須 |
| 計測設計（GTM） | フォーム送信、CTA クリック（お問い合わせ／サービスを見る）、スクロール深度、外部リンククリックをイベント化。GA4 でコンバージョン設定 | 必須 |
| Search Console 登録 | サイトマップ送信、インデックス状況・検索クエリの確認 | 必須 |
| Google ビジネスプロフィール | 事業所情報を公開できる場合のみ。地域検索（「大阪 システム開発」等）の入口になる | 高 |
| OGP・メタ情報 | SNS で共有された際の見え方を整える（開発計画フェーズ2と連動） | 高 |

> GTM で解析タグを入れる場合、Cookie 等の利用についてプライバシーポリシーへの明記が必要です。

### 4.2 コンテンツ（検索流入の中核）

サイトの Journal は「設計」「技術」「仕事」の 3 テーマで構成されています。これを検索流入の入口として育てます。

| 軸 | 記事テーマ例 | 狙う読者 |
| --- | --- | --- |
| 設計の話 | 要件定義でやること・やらないこと／発注前に決めておくべき 5 項目／システム開発の見積もりが変わる理由 | A・B |
| 技術の話 | 小さく始める Web サービスの技術選定／既存システムを作り直すか改修するかの判断基準 | B・C |
| 仕事の話 | 小さな会社が一貫して関わる意味／保守を前提にした設計とは | A・B |

- 頻度: **月 2 本**を目安（難しければ月 1 本でも継続を優先）
- 1 記事 = 1 つの検索意図。末尾に関連サービスへの導線と問い合わせ導線を置く
- 記事の管理方式は開発計画「判断事項 #4」に従う（当初はコンポーネント内の配列、増えたら Markdown 化）
- 公開前に、顧客名・案件の特定につながる情報が含まれないか確認する

### 4.3 実績・信頼の可視化

現状は「個別の導入事例や顧客名は掲載していません」としています。信頼獲得のため、以下の順で段階的に開示します。

1. **匿名化した事例**（業種・課題・進め方・成果を、顧客が特定されない形で）
2. **お客様の声**（許諾が取れたものを、社名なし・業種のみ等で）
3. **自社の取り組み**（自社ツール・検証記事・技術メモ）を Works に追加
4. 許諾が得られた場合のみ、社名・ロゴ付きの事例

### 4.4 チャネル別施策

| チャネル | 役割 | 内容 | 時期 |
| --- | --- | --- | --- |
| 自然検索（SEO） | 中長期の主軸 | Journal 記事、ローカル検索対策（地域名×サービス名） | 公開直後〜継続 |
| 紹介・人脈 | 初期の最有力 | 既存の取引先・知人・同業パートナーへの案内。紹介時に渡せる 1 枚資料（会社概要・進め方）を用意 | 公開直後 |
| SNS（X / Facebook / LinkedIn のうち 1〜2 つ） | 記事の拡散・認知 | Journal 更新の告知、設計や技術の短い解説。更新負荷を考え、**最初は 1 媒体に絞る** | 公開後 1 か月〜 |
| 地域コミュニティ・勉強会 | 信頼構築 | 大阪の IT・中小企業向けイベントへの参加／登壇。登壇資料を記事化 | 3か月〜 |
| 外部媒体への掲載 | 被リンク・信頼 | 技術ブログサービス（Qiita / Zenn 等）への転載・要約。**元記事へのリンク**を付ける | 3か月〜 |
| 有料広告（検索連動型） | 検証用 | 「大阪 業務システム 開発」等の限定キーワードを少額でテスト。成果が見えるまで拡大しない | 6か月〜（任意） |
| 比較・マッチングサイト | 補助 | 受託開発の比較サイトへの登録は手数料・案件単価を確認のうえ要否判断 | 任意 |

### 4.5 問い合わせから受注までの流れ（営業プロセス）

1. 問い合わせ受信 → 自動返信（受付通知）
2. **営業日 1 日以内**に個別返信（初回ヒアリング日程の提案）
3. 初回ヒアリング（無料・30〜60 分）: 課題・予算感・期限・体制を確認
4. 提案・概算見積（要件整理を有償の準備フェーズとして切り出す提案も検討）
5. 契約・着手
6. 納品後のフォロー（保守契約の提案、紹介の依頼、お客様の声の依頼）

問い合わせ管理（受付日・流入元・案件種別・ステータス）を、スプレッドシート等で最初から記録します。

## 6. 計測（KPI）

GTM / GA4 / Search Console で計測します。

| 区分 | 指標 | 見る頻度 |
| --- | --- | --- |
| 流入 | セッション数、流入元別（検索・SNS・紹介・直接）、検索クエリ・表示回数 | 月次 |
| 行動 | CTA クリック率、スクロール深度、Journal 記事の閲覧数 | 月次 |
| 成果 | **問い合わせ数（フォーム送信）**、流入元別の問い合わせ数、問い合わせ→商談→受注率 | 月次 |
| コンテンツ | 公開記事数、記事別の流入・問い合わせ貢献 | 月次 |
| 品質 | Lighthouse スコア、Core Web Vitals | 四半期 |

- イベント設計（GTM）: `form_submit`、`cta_click`（位置・文言をパラメータに）、`outbound_click`、`scroll_depth`
- 月次で 30 分の振り返りを行い、記事テーマ・導線を調整する

## 8. リスクと対策

| リスク | 対策 |
| --- | --- |
| 記事更新が続かない | 月 1 本でも継続。テーマを先に 10 件ストックし、1 記事の長さと型を固定する |
| 実績がなく信頼が得にくい | 匿名事例・自社取り組み・プロフィール公開で補う。初回相談を無料にして心理的ハードルを下げる |
| 問い合わせへの対応遅れ | 返信ルール（営業日 1 日以内）を決め、通知がメール等に確実に届く設定にする |
| 個人情報・顧客情報の漏えい | 事例・記事の公開前に匿名化チェック。フォーム送信先サービスの保存場所・保持期間を確認 |
| 計測が機能しない | 公開直後に GTM プレビューでイベント発火を確認。GA4 のリアルタイムで検証 |
